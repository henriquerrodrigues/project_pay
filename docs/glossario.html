1. Domínio do PIX (o "mundo real")

Project Pay simula, em escala reduzida, o ecossistema real do PIX brasileiro. Estes são os conceitos emprestados do mundo real que o sistema modela ou simplifica.

SPI — Sistema de Pagamentos Instantâneos planejado

Câmara de compensação e liquidação do PIX operada pelo Banco Central. Processa transferências entre participantes (bancos) em tempo real, 24/7, com liquidação bruta em tempo real (LBTR) — cada transação liquida individualmente, sem lote. Tempo regulatório: menos de 10 segundos ponta a ponta.

No Project Pay hoje, uma única instância do serviço simula "um banco só" — não existe roteamento entre participantes. Isso é o objetivo da Fase 3 do plano mestre ("SPI simulado").

DICT — Diretório de Identificadores de Contas Transacionais em andamento

Banco de dados centralizado do BACEN que mapeia "chave PIX" → conta bancária. Quando alguém digita uma chave, o banco pagador consulta o DICT antes de transferir.

Equivalente simplificado no projeto: entidade PixKey — resolve chave → conta, mas dentro de uma única base, sem portabilidade entre bancos nem claims.

ISO 20022 planejado

Padrão internacional de mensagens financeiras baseado em XML. O PIX usa um subconjunto chamado "Pix Payments", com mensagens como pacs.008 (instrução de crédito banco-a-banco) e pacs.002 (confirmação/status).

Project Pay usa JSON em vez de XML por simplicidade de integração HTTP — uma simplificação deliberada, documentada no diário de bordo (Dia 01). A semântica de campos (EndToEndId, ISPB) é preservada mesmo sem o XML real.

EndToEndId implementado

Identificador único e imutável de uma transação PIX, do início ao fim (mesmo atravessando bancos diferentes). Formato adotado no projeto: E + ISPB (8 dígitos) + YYYYMMDD + HHMM + sufixo aleatório (11 caracteres).

Exemplo real gerado no projeto: E60074319020260517142300A3F9C12D8. Implementado em repositories/transfers, função generateEndToEndID.

ISPB — Identificador do Sistema de Pagamentos Brasileiro implementado

Código de 8 dígitos que o Banco Central atribui a cada instituição financeira participante do sistema de pagamentos — o "CPF do banco". No projeto, vive no campo Participant.Ispb.

Conta Reservas planejado

Mecanismo real de liquidação: cada banco participante mantém uma conta no BACEN, e a liquidação bruta debita/credita essas contas diretamente, transação por transação.

Não modelado ainda — só faz sentido quando existir mais de um "banco" simulado (Fase 3).

pacs.008 / pacs.002 planejado

pacs.008 é a mensagem "quero transferir X do Banco A pro Banco B"; pacs.002 é a confirmação (ou erro) de volta.

Equivalente simplificado hoje: POST /transfers devolve o próprio recurso Transfer com status — sem troca de mensagens entre serviços, porque só existe um serviço.

2. Entidades do sistema

As tabelas/models que existem hoje no banco (ver migrations/ e cmd/internal/models/).

User implementado

Dono de uma ou mais contas. Campos: id, name, email, tax_id, created_at (+ senha com hash bcrypt, não exposta no JSON).

Participant implementado

Representa "o banco" — uma instituição participante do sistema de pagamentos. Campos: id, ispb, name, created_at.

Account implementado

Conta bancária vinculada a um User e a um Participant. Campos: id, userID, participantID, accountNumber, branch, accountType (cacc = corrente, svgs = poupança), balance (inteiro, menor unidade monetária — evita ponto flutuante), createdAt.

Transfer implementado

Uma transferência entre duas contas. Campos: id, endtoendID, senderAccountID, receiverAccountID, amount, status, description, createdAt, completedAt (nullable — *time.Time).

LedgerEntry — lançamento contábil implementado

Cada Transfer gera dois lançamentos: um DEBIT na conta de origem, um CREDIT na conta de destino. Campos: id, transfer_id, account_id, amount, entry_type, balance_after (saldo após o lançamento — histórico auditável), created_at.

É a base do extrato (GET /accounts/{id}/statement) e do que a Semana 7 do plano mestre vai explorar com window functions.

PixKey implementado

Chave PIX vinculada a uma conta — o equivalente simplificado do DICT. Campos: id, keyType, keyValue, accountID, createdAt.

3. Arquitetura de código

Handler (HTTP)  →  Service (regra de negócio)  →  Repository (SQL puro)
    ↓                      ↓                              ↓
parsing JSON      validação, ownership,              queries pgx,
+ status HTTP     apperrors.*                        transações
Handler implementado (parcial — só users migrado)

Faz parsing do JSON de entrada, chama o Service, e repassa o resultado (ou erro) como resposta HTTP. Não decide regra de negócio nem status HTTP — isso vem do erro tipado devolvido pelo service.

Service em andamento

Camada onde vive a regra de negócio: validação de campos, ownership (dono do recurso), tradução de falha em erro tipado (apperrors). Declara uma interface pequena do repository que precisa, permitindo testes com fakes em memória (sem banco real).

Hoje: services/users completo; services/accounts parcial (só ListByCurrentUser); participants, pix_keys, ledger_entries, transfers, auth ainda não iniciados.

Repository implementado

Só fala SQL — nenhuma regra de negócio aqui. Usa pgx (não database/sql puro), ver ADR-0001 em docs/adr/.

apperrors implementado

Pacote com o tipo Error (código de máquina + status HTTP + mensagem segura + causa interna não exportada), construtores (NotFound, InvalidInput, Unauthorized, Forbidden, InsufficientFunds, Internal), e WriteHTTP — converte qualquer error na resposta JSON padrão {"code","message","trace_id"}, sem vazar detalhe interno.

traceid implementado

Pacote minúsculo que guarda um ID de correlação no context.Context, usando uma chave de tipo não exportado (evita colisão). Existe separado de middleware/apperrors pra evitar ciclo de import entre os dois.

middleware.Auth + UserIDFromContext em andamento

Middleware que valida o JWT (Bearer token) e injeta o user_id no context. UserIDFromContext(ctx) é o helper que os services usam pra aplicar ownership.

O middleware em si ainda usa http.Error cru em vez do contrato apperrors — migração planejada junto com o service de auth.

Ownership (dono do recurso) em andamento

Regra aplicada nos services: recurso inexistente → 404 NOT_FOUND; recurso existente mas de outro usuário → 403 FORBIDDEN. Aplicado hoje em users.GetByID; planejado para accounts, transfers e ledger_entries.

RequestLogger + slog planejado

Middleware que envolveria o mux inteiro: gera um trace ID por requisição, injeta no header X-Trace-Id e no context, loga método/rota/status/duração em JSON estruturado.

4. Passo a passo — uma transferência de ponta a ponta (visão atual)

  1. Login — POST /auth/login com email/senha → valida via bcrypt → devolve JWT.
  2. Criar conta — POST /accounts (autenticado) → dono vem do token, nunca do body.
  3. Consultar contas — GET /accounts lista as contas do usuário logado.
  4. Transferir — POST /transfers: dentro de uma transação SQL —
    1. SELECT ... FOR UPDATE trava a linha da conta de origem
    2. valida saldo suficiente
    3. gera o EndToEndId
    4. debita origem, credita destino (UPDATE ... RETURNING)
    5. insere o registro em transfers
    6. insere dois ledger_entries (DEBIT + CREDIT)
    7. COMMIT
  5. Ver extrato — GET /accounts/{id}/statement lista os ledger_entries da conta.
⚠️ Ponto conhecido de fragilidade (proposital): o FOR UPDATE evita corrupção de saldo numa única instância de banco, mas não resolve duplicação por retry de rede (o cliente reenviando a mesma transferência). Isso é intencional — a Semana 6 do plano mestre existe justamente pra provar essa e outras falhas antes de corrigi-las na Fase 2.

6. Glossário do que vem depois (planejado, ainda não desenvolvido)

Documentado agora por antecipação — conforme cada item for implementado, troque o selo planejado para implementado.

Idempotência (chave de idempotência) planejado — Fase 2

Mecanismo pra garantir que reenviar a mesma requisição (retry de rede) não duplica o efeito. Normalmente: cliente envia uma chave única por operação; servidor guarda numa tabela de deduplicação e recusa/repete a resposta anterior se a chave já foi vista.

Locking pessimista (SELECT FOR UPDATE) implementado (versão simples)

Trava a linha no banco durante a transação, impedindo leitura/escrita concorrente até o COMMIT. Já usado em transfers hoje; será comparado formalmente com locking otimista na Fase 2.

Locking otimista (versão de linha) planejado — Fase 2

Em vez de travar a linha, guarda um número de versão; a escrita só é aceita se a versão não mudou desde a leitura. Menos contenção, mas exige lidar com conflito (retry) no nível da aplicação.

Outbox pattern planejado — Fase 2

Padrão pra publicar eventos de domínio com garantia de entrega: a escrita no banco e a intenção de publicar o evento acontecem na mesma transação (tabela outbox); um processo separado lê essa tabela e publica de fato na fila, evitando o cenário "salvei no banco mas a mensagem se perdeu".

RabbitMQ planejado — Fase 2

Mensageria que vai separar o sistema em dois serviços: pagar-api (recebe HTTP) e pagar-processor (consome fila e processa a transferência de fato).

Redis planejado — Fase 2

Cache de leitura de saldo (com invalidação cuidadosa) e lock distribuído para operações que atravessam múltiplos serviços.

Padrão Saga planejado — Fase 3

Estratégia pra manter consistência em operações que atravessam múltiplos serviços/bancos sem transação distribuída clássica: cada etapa tem uma "compensação" (ação reversa) caso uma etapa posterior falhe.

Chaos testing planejado — Fase 3

Derrubar serviços deliberadamente em produção/staging pra observar e documentar como o sistema se recupera (ou não).

Keyset pagination planejado — Semana 7

Estratégia de paginação que usa um cursor (ex: último id+created_at visto) em vez de OFFSET, evitando degradação de performance conforme a tabela cresce.

k6 (testes de carga) planejado — Semana 6

Ferramenta usada pra gerar carga concorrente sobre a API e provar cientificamente falhas como saldo negativo (race condition) e débito duplicado (falta de idempotência) — documentadas depois em docs/patologias.md.

Observabilidade (Prometheus/Grafana/OpenTelemetry) planejado — Semanas 9-10 (básico), Fase 3 (completo)

Métricas (contadores, histogramas, gauges), dashboards e traces distribuídos que atravessam múltiplos serviços — complementa os logs estruturados com trace ID que já existem desde a Semana 3.

Detecção de fraude (isolation forest / ML) planejado — Fase 4

Serviço em Python consumindo o stream de eventos do RabbitMQ, treinado com dados sintéticos de fraude injetados propositalmente, capaz de sinalizar transferências suspeitas de volta à API.
